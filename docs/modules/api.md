# api Module

> **Living document.** Read this before modifying the module. Update it in the same change whenever the module's behavior, endpoints, files, or dependencies change.

**Source:** `api/` · **Last verified:** 2026-08-01

## Purpose

`@grantfox/api` — the Postgres-backed indexer package for the privacy
wallet. Task 5 shipped the schema, the drizzle client factory, and the
`IndexerRepo` data-access surface. Task 6 added the two event sources:
`fetchRpcEvents` (Soroban RPC `getEvents`) and `fetchBootnodeEvents` (the
SPP bootnode's cached `getEvents`, used to bootstrap history past the RPC's
retention window until it hands off back to the RPC) — both return the
same `EventsPage` shape. Task 7 adds the polling engine
(`api/src/modules/indexer/poller.ts`: `pollStream`/`pollStreams` + the two
`StreamSource` factories) and the worker process (`api/src/worker.ts`) that
drives it on an interval, with per-stream exponential backoff and isolation
and a graceful-shutdown loop. Task 8 adds the CT normalizer
(`api/src/modules/indexer/normalize-ct.ts`: `normalizeCtEvent`, pure) and
wires it into `pollStream` as a post-insert step inside the SAME
transaction as the raw-event insert, CT stream only (`ctTokenId` param) —
`worker.ts`'s CT stream state now carries `TESTNET.ct.token` so every CT
event the worker fetches also lands normalized `ct_activity` rows. No HTTP
server exists yet (Task 9).

**Task 8.5 (this update) — SPP historical backfill from an archival
source.** Both of Task 7's live SPP sources turned out to be permanently
dead for the SPP pool's actual history: the RPC's retention window starts
AFTER the pool's deployment ledger (see the "Live-verification blocker"
gotcha below), and Nethermind's public bootnode rejects every filter set
tried with `-32602 unsupported filters`. Task 8.5 recovers that history
from stellar.expert's public archive instead — `api/scripts/backfill-spp.ts`
fetches all 4 of the SDK's sync-set contracts' events (asc, complete to
tip), resolves each event's `txHash` via Horizon testnet, and writes a
deterministic, committed fixture (`api/fixtures/spp-backfill.json`).
`api/scripts/load-backfill.ts` loads that fixture into `events`
(idempotent, on-conflict-do-nothing — same mechanism as the live pollers)
and initializes the worker's SPP stream cursor straight to RPC mode, so the
worker's very next poll for that stream skips the dead bootnode entirely.
Backfilled rows are produced by `api/src/lib/spp-archive.ts`'s
`mapArchiveRecordToRawEvent`, which REUSES `soroban-events.ts`'s
`naturalEventId`/`eventIndexFromId` so a row is byte-identical in shape
(same `events.id` format, same base64-XDR topic/value representation)
whether it came from stellar.expert, the RPC, or (hypothetically) the
bootnode.

| `api/src/modules/indexer/poller.ts` | The polling engine. `pollStream(source, repo, streamKey, ctTokenId?): Promise<void>` — one page per call: fetch (network I/O, outside any transaction), then `repo.withTransaction` batch-inserts events, then (Task 8, only when `ctTokenId` is passed) runs each fetched event through `normalizeCtEvent` **inside a per-event try/catch** (review fix, see Gotchas) and `insertCtActivity`s the surviving rows — all as one post-insert step INSIDE the same transaction — then advances the cursor, all as one unit. `pollStreams(streams, repo, shouldStop?)` — runs `pollStream` per stream (forwarding each `StreamConfig`'s optional `ctTokenId`) with per-stream try/catch isolation, returning `{streamKey, ok, error?}[]`; `shouldStop` (optional) is checked between iterations (never mid-flight) so a shutdown signal can skip streams not yet started (review fix, see Gotchas). `StreamSource` — the fetch abstraction (`fetchPage(cursor): Promise<{events, nextCursor}>`); `makeRpcSource(config)` (pure-RPC, the CT stream) and `makeBootnodeThenRpcSource(config)` (bootnode-until-handoff-then-RPC, the SPP stream) are the two concrete factories, both taking an optional `timeoutMs` (review fix) and each injectable with a fake `fetchEvents`/`fetchBootnode` for tests. Owns the cursor-value encoding (`ledger:<N>`, `handoff:<N>`, `rpc:<...>`) documented in the file's module doc comment. |
| `api/src/modules/indexer/poller.test.ts` | TDD spec for the five invariants (batch+cursor atomicity; cursor advances past a filtered page; resume-from-cursor with no duplicate `events.id`; bootnode handoff → RPC switch, restart-safe; per-stream error isolation) plus `makeRpcSource` unit cases, a `pollStreams`/`shouldStop` early-exit case, and (Task 8) a `describe` block proving the CT-normalization wiring: passing `ctTokenId` normalizes fetched events into `ct_activity` rows in the SAME transaction; a non-CT-activity event still inserts its raw row but no `ct_activity` row; omitting `ctTokenId` (the SPP call site) never touches `ct_activity` even for a normalizable event; a mid-transaction crash rolls back the `ct_activity` insert too, not just the cursor; and (review fix) a page with ONE poisoned event (a valid mapped topic but a value XDR `normalizeCtEvent` throws on) still inserts BOTH raw events, still inserts the good event's `ct_activity` row, still advances the cursor, and logs the failure with the offending event's id (asserted via a `console.error` spy). Offline via an in-memory `FakeRepo` with REAL stage/commit/rollback transaction semantics (not a stub) for invariant 1's and the CT-wiring rollback case's proof; two `describe.skipIf(!DATABASE_URL)` blocks re-prove invariant 1 and the CT wiring against real Postgres. |
| `api/src/modules/indexer/normalize-ct.ts` | The CT normalizer (Task 8). `normalizeCtEvent(raw: RawEvent, tokenId: string): CtActivityInsert[] \| null` — pure (no I/O, no `Date.now()`): returns `null` if `raw.contractId !== tokenId`, if `raw.topic` is empty, or if `topic[0]`'s symbol isn't one of `register`/`deposit`/`merge`/`withdraw`/`transfer`. Otherwise decodes the topics/value XDR (`xdr.ScVal.fromXDR` + `Address.fromScVal`/`scValToNative`/`.bytes()`) and maps to `ct_activity` row(s): `register`/`merge` → one self-row, no amount, empty `ciphertexts`; `deposit` → a row per side (collapsed to one when `from === to`), public `amount`, empty `ciphertexts`; `withdraw` → one row for `from` only, public `amount`, `ciphertexts` = the 4 checkpoint fields (`rE`/`sigma`/`bTilde`/`bAudS`); `transfer` → a row per side (also collapsed to one when `from === to`, same rationale as `deposit`), `amount: null`, `ciphertexts` = the full 8-field set (adds `vTilde`/`vAudR`/`rAudR`/`vAudS`). Ciphertext values are `0x`-prefixed lowercase hex of the RAW on-chain `BytesN` bytes — not decoded through any curve-point math (see Gotchas: field names). **Deliberately fail-fast, not defensive** (review fix, see Gotchas): a malformed/missing value field throws rather than being swallowed — `poller.ts` owns per-event error isolation, not this function. `CtActivityInsert` is an exported alias for `NewCtActivityRow`. |
| `api/src/modules/indexer/normalize-ct.test.ts` | TDD spec against 13 REAL events fetched live from the deployed CT contract (`__fixtures__/ct-events.json`, committed; provenance and decode-transcript pointer in the file's module doc). Covers: non-CT-activity topics (the 4 constructor-setter events) → `null`; contractId mismatch → `null`; empty `topic` → `null`; a CT-emitted-but-unmapped event (`spender_transfer`, XDR round-trip-verified, not hand-encoded) → `null`; register (2 real events, one C-address one G-address account); deposit (self-deposit → 1 row; a synthesized cross-account variant → 2 rows, same amount); merge; transfer (2 rows, `amount: null`, all 8 hex ciphertext fields asserted against hand-decoded values, plus a synthesized self-transfer → 1 row, review fix); withdraw (1 row, public amount, 4 hex ciphertext fields); purity (no input mutation; deterministic same-input-twice); and (review fix) a fail-fast case — real `withdraw` topics paired with a real `register` event's `valueXdr` (missing the fields `withdraw` needs) asserts `normalizeCtEvent` THROWS rather than returning `null`/a partial row. |

## Gotchas & invariants

- `insertEvents` is on-conflict-do-nothing **by `id` only** — a re-inserted row with the same id but different payload is silently ignored (the first write wins). This is intentional for idempotent worker restarts, but means a genuine data-correction requires a manual `UPDATE`, not a re-insert.
- `insertBootnodePage` is also on-conflict-do-nothing by `cursorIn`, same idempotency rationale — a page fetch for an already-cached `cursorIn` is a no-op even if `response` would differ.
- `setCursor` is a real upsert (`onConflictDoUpdate`), unlike the two above — cursors are meant to move forward and always reflect the latest value.
- `withTransaction`'s callback receives a `RepoOps` bound to the transaction handle (not the outer `IndexerRepo`), so it can call any insert/query helper but not nest another `withTransaction`.
- `ct_activity.amount` is the only nullable column in the schema; everything else (including `bootnode_pages.cursor_out` / `last_event_ledger`) is `NOT NULL` per the task-5 brief's literal column list — there was no signal to make anything else optional.
- `cursors.updated_at` and `bootnode_pages.created_at` default to `now()` at the DB level (`defaultNow()`), not application code — this wasn't spelled out in the brief but matches the "troqpay shape" convention for timestamped audit tables.
- `api/tsconfig.json` excludes `src/**/*.test.ts` from the `build` output — test files are type-checked by `vitest` (esbuild transpile, not full `tsc`) and separately by a full-tree `tsc --noEmit` during review, not by `pnpm build`.
- `fetchRpcEvents`/`fetchBootnodeEvents` both derive `RawEvent.id` as `${ledger}-${txHash}-${opIndex}-${eventIndex}`; `opIndex`/`txIndex` come directly off sdk-16's `operationIndex`/`transactionIndex` fields (no toid bit-masking needed, unlike `@ctd/sdk`'s older-SDK-targeting `rpcEventCoords`), but `eventIndex` still has no dedicated field on either source and is parsed from the second segment of the event `id` (`<toid>-<eventOrder>`) by the shared `eventIndexFromId` helper.
- `RawEvent.topic`/`valueXdr` are base64-encoded XDR strings for BOTH sources, not decoded native values — `fetchRpcEvents` re-encodes the SDK's parsed `xdr.ScVal`s via `.toXDR("base64")`; `fetchBootnodeEvents` passes the bootnode's already-base64 wire strings straight through. Decoding to CT-specific native values (event names, addresses, amounts) is left to the normalizer (Task 8), not done here.
- `fetchRpcEvents` throws if an `EventResponse.contractId` is `undefined` — it does NOT fall back to a single "requested" contract id (unlike troqpay's `soroban-gateway.ts`, whose `getContractEvents` fell back to its one request-scoped `contractId`), because this adapter filters by potentially MULTIPLE `contractIds` and a wrong fallback would silently mislabel a row's contract.
- `fetchBootnodeEvents` throws if a mapped event is missing `operationIndex`/`transactionIndex`/`txHash`/`inSuccessfulContractCall` (all `Option` on the bootnode's Rust `Event` struct) — the `events` table requires them `NOT NULL` and the id can't be built without `txHash`/`operationIndex`, so this adapter fails fast rather than guessing.
- The bootnode's wire params nest `cursor`/`limit` under `params.pagination`, NOT flat on `params` — `GetEventsParams` is `#[serde(deny_unknown_fields)]` server-side, so a flat body is rejected. Neither `soroban-events.ts` nor `bootnode-client.ts` retries or logs; `poller.ts`/`worker.ts` own all retry/backoff policy (including on `BootnodeCacheMissError` — an ordinary caught error, backed off like any other stream failure, no special-casing needed).
- **Both network adapters are timeout-bounded, `DEFAULT_FETCH_TIMEOUT_MS` = 30s, injectable per-call as `timeoutMs`** (Task 7 review fix — before this, a hung fetch on one stream blocked `pollStreams`' sequential loop indefinitely, and since `worker.ts`'s `while` loop only checks its shutdown flag BETWEEN `tick()` calls, a hang meant SIGTERM never produced the documented clean exit). `fetchBootnodeEvents` uses a plain `AbortController`+`setTimeout` (its own `fetch` call). `fetchRpcEvents` is the more interesting one: `RpcServer.Options.timeout` — the CONSTRUCTOR option `server.d.ts` documents — is a **dead type in the installed sdk-16.2.0 build**; `new RpcServer(url, opts)`'s actual (transpiled) constructor only ever reads `opts.headers`/`opts.allowHttp`, never `opts.timeout` (verified by reading `rpc/server.js`, not trusting the `.d.ts`). The mechanism that DOES work: `server.httpClient.defaults.timeout = ms`, mutating the mutable `HttpClientDefaults` object the SDK's own doc-comment example shows is a supported pattern (`server.httpClient.defaults.headers[...] = ...`) — `getEvents`'s call path merges `httpClient.defaults` into every request and (since no `maxRedirects`/`maxContentLength` is set) routes through the `feaxios` dependency's `instance.request`, which genuinely honors `config.timeout` via `AbortSignal.timeout` and rejects with a plain `AxiosError` on expiry. Covered by a "wiring" test in `soroban-events.test.ts` (captures `this.httpClient.defaults.timeout` inside a `getEvents` mock) rather than a live-hang test, since the SDK's `getEvents` is normally mocked wholesale in tests (`vi.spyOn(rpc.Server.prototype, "getEvents")`), bypassing the HTTP layer entirely.
- `pollStreams(streams, repo, shouldStop?)`'s `shouldStop` is checked only BETWEEN streams, never mid-flight — a stream already in progress when a shutdown signal arrives always runs to completion or its own timeout. This bounds `tick()`'s shutdown-triggered worst case to "at most one stream's timeout" rather than "every remaining stream's timeout summed," without restructuring the sequential for-loop into concurrent execution. `worker.ts`'s `main()` passes `() => shuttingDown` as `tick`'s `shouldStop`.
- **Cursor-value encoding is meaningful, not opaque, for the two `poller.ts` source factories** — see the file's module doc comment for the full state machine. Short version: `null` = start from configured `startLedger`; a bare string = an opaque cursor from the underlying source passed straight back; `ledger:<N>` = a synthesized fallback when a page reports `cursor: null` (EventsPage's "no further cursor" case — neither `fetchRpcEvents` nor `fetchBootnodeEvents` accepts a bare ledger number as `cursor`, so this marker is decoded back into a `startLedger` fetch, never sent to the network as-is); `handoff:<N>` (SPP only) = the literal transitional marker the task brief asks for, persisted the instant the bootnode reports a retention handoff; `rpc:<...>` (SPP only) = wraps EVERY subsequent cursor once handed off, which is what makes the handoff survive a worker restart — `makeBootnodeThenRpcSource` decides "bootnode or RPC?" purely by reading this prefix off the persisted string, never from in-memory state.
- `pollStream` reads the cursor and calls `source.fetchPage` (network I/O) BEFORE opening the transaction — a transaction is never held open across a network call. Only the insert + `setCursor` happen inside `repo.withTransaction`.
- A page with `nextCursor !== null` always advances the cursor even when `events` is empty (invariant 2) — `insertEvents([])` is `RepoOps`'s documented no-op, `setCursor` still runs. `pollStream` only skips `setCursor` if a `StreamSource` ever returns a literal `null` `nextCursor`, which neither shipped factory does (they always synthesize `ledger:`/`handoff:`/`rpc:` instead) — this is a defensive branch, not exercised by the shipped sources.
- **`api/package.json`'s `test` script runs `vitest run --no-file-parallelism`** (Task 7) — vitest's default is to run test FILES concurrently, and with two DB-integration test files now sharing the same live local-Postgres tables (`repo.test.ts` and `poller.test.ts`'s `describe.skipIf(!DATABASE_URL)` block, both `beforeEach`-truncating `events`/`ct_activity`/`cursors`/`bootnode_pages`), concurrent files raced: one file's truncate could fire mid-assertion in the other, observed as a rare, non-deterministic `ct_activity` row-count failure in `repo.test.ts` (not caused by a bug in either file's own logic — confirmed reproducible only under file-level parallelism, gone after 10/10 clean runs with the flag). Any FUTURE integration test file added to this package should assume it may run interleaved with these two unless this flag stays in place.
- **`normalize-ct.ts`'s on-chain field names follow the FIXTURES, not the checked-out `resources/stellar-contracts` Rust source (Task 8, verified 2026-08-01).** The deployed testnet CT contract's real event data-map field names (`r_e`, `sigma`, `b_tilde`, `b_aud_s`, `v_tilde`, `v_aud_r`, `r_aud_r`, `v_aud_s` — decoded straight from `__fixtures__/ct-events.json`'s `valueXdr`) match the vendored `@ctd/sdk`'s `packages/ctd-sdk/src/chain/events.ts` `buildConfidentialEvent` mapping EXACTLY (event names, topic layout, and both the snake_case on-chain names and their camelCase row-field names `rE`/`vTilde`/`sigma`/`bTilde`/`vAudR`/`rAudR`/`vAudS`/`bAudS` — cross-checked line-by-line against `events.ts:167-193`). They do NOT match the branch checked out at `resources/stellar-contracts` (`feat/confidential-verifier-ultrahonk`, `packages/tokens/src/confidential/mod.rs`), which has since renamed several fields (e.g. `b_aud_s` → `b_tilde_aud_s`) — the deployed contract predates that rename. If `resources/stellar-contracts` is ever updated to a build matching the rename, `normalize-ct.ts` and its fixtures need re-verifying against a fresh live capture before trusting the Rust source over the fixtures again.
- `normalize-ct.ts`'s `ciphertexts` values are `0x`-prefixed lowercase hex of the RAW on-chain `BytesN<32>`/`BytesN<64>` bytes (`val.bytes()`, no curve-point decode) — a deliberate choice to avoid depending on `@ctd/sdk`'s crypto helpers (`pointFromBytes`/`fromBytesBE`, which pull in the zk-proving stack `@aztec/bb.js`/`@noir-lang/noir_js`, same rationale as the `events.id` gotcha above). The wallet client (Task 11) decodes these hex strings itself with the same byte layout those helpers expect — this is why `withdraw`'s `rE` (a `Point`, 64 bytes) and `sigma`/`bTilde`/`bAudS` (field elements, 32 bytes) can share one `hexBytes()` helper: the normalizer never needs to know which is which, only the wallet does.
- **`withdraw` produces a row for `from` ONLY, not `to`** (task-8-brief.md's literal wording) — `to` merely receives plain SEP-41 tokens leaving the confidential system and isn't a CT-tracked account for this event. `deposit` and `transfer` both collapse to a SINGLE row (not two identical ones) when `from === to` — a self-deposit/self-transfer is a real on-chain pattern in the fixtures (e.g. fixture 8, ledger 3900642) and emitting two identical rows would double-count that one action in that one account's activity feed.
- `normalizeCtEvent` returns `null` (not an empty array) for anything it doesn't map: wrong `contractId`, zero topics, a non-symbol `topic[0]`, or a real CT-emitted event outside its five-name whitelist (`spender_transfer`/`set_spender`/`revoke_spender`/the compliance events/the four constructor-setter events seen live in the fixtures).
- **Per-event error isolation is `poller.ts`'s job, not `normalize-ct.ts`'s (review fix, 2026-08-01).** `normalizeCtEvent` is deliberately fail-fast: a malformed/missing value field (`requireField`) or an undecodable topic throws, it does not return `null`/a partial row/swallow the error. Originally `pollStream`'s wiring called it bare inside `events.flatMap(...)` — so ONE malformed event threw out of the whole `repo.withTransaction` callback, rolling back the ENTIRE page's raw-event insert and skipping the cursor advance; the next poll would refetch the identical poisoned page and fail identically, forever (a permanent stall, not just a dropped event — worse than doing nothing). Fixed: `pollStream` now calls `normalizeCtEvent` inside a per-event try/catch, `console.error`-logs the failure (with the offending event's `id`, so it's greppable/alertable in production logs) and continues — that ONE event contributes zero `ct_activity` rows but its raw `events` row still inserts, every other event on the page still normalizes normally, and the cursor still advances past the whole page. The foreseeable trigger this guards against is the one `normalize-ct.ts`'s own module doc already flags: a redeployed CT contract whose event field names have drifted (the `b_aud_s` → `b_tilde_aud_s` rename already observed on `resources/stellar-contracts`' current branch, not yet on the deployed contract this normalizer targets). Covered by `poller.test.ts`'s "poisoned CT event" case (asserts both raw events insert, only the good event's activity row inserts, the cursor still advances, and the log fires with the event id) and `normalize-ct.test.ts`'s fail-fast case (asserts the throw itself, proving `normalizeCtEvent` was never made defensive — only its caller was).
- `pollStream`'s per-event loop treats a `null` return the same as an empty array (`if (rows !== null) activityRows.push(...rows)`), so the `null`-vs-`[]` distinction above only matters to `normalizeCtEvent`'s own callers/tests, not to the wiring.
